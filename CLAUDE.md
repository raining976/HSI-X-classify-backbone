# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Environment and common commands

- Preferred environment: `conda env create -f environment.yml && conda activate HSI-X-Classify-Backbone`
- Alternate install: `pip install -r requirements.txt`
- Show available wrapper commands: `make help`
- Train using the default config file or quick config fallback: `make train` or `python scripts/train.py`
- Test using the script defaults: `make test` or `python scripts/test.py`
- Smoke-train for 1 epoch with the script defaults: `make strain` or `python scripts/strain.py`
- Smoke-test with capped samples: `make stest` or `python scripts/stest.py`
- Batch-run models/datasets, skipping missing datasets: `make train-all` or `python scripts/train_all.py`
- Show script help:
  - `make htrain`
  - `make htest`
  - `make htrain-all`
  - `python scripts/train_all.py -h`

## Config-driven workflow

`scripts/train.py` is config-file-first, not a full training CLI. It loads `configs/train.json` if present, otherwise falls back to a hardcoded quick config in [scripts/train.py](scripts/train.py). To change routine training behavior, edit `configs/train.json` rather than patching the script.

Useful config/test patterns:

- Train with the checked-in config: `python scripts/train.py --config configs/train.json`
- Point training at another config file: `python scripts/train.py --config path/to/other.json`
- For quick smoke runs, prefer `scripts/strain.py` or create a temporary config rather than rewriting training defaults.
- `scripts/test.py` uses its own quick config defaults and does not load `configs/train.json`.

The repository also has a reusable CLI config builder in [src/config.py](src/config.py). The main entrypoints do not fully expose it yet, but it is the canonical place for adding future CLI-driven experiment launchers.

## Architecture overview

This codebase is a unified experiment harness for HSI + auxiliary modality classification (LiDAR / SAR / MSI). The important architectural idea is that model code is intentionally isolated behind adapters so the training/evaluation pipeline can treat all models the same.

End-to-end flow:

1. A script in `scripts/` constructs or loads an `ExperimentConfig`.
2. [src/runner.py](src/runner.py) initializes global config state and dispatches train/test.
3. [src/trainer.py](src/trainer.py) or [src/evaluator.py](src/evaluator.py) asks [src/data.py](src/data.py) for loaders.
4. `src.data` reads `.mat` files, applies PCA to HSI, normalizes HSI/X, builds patch datasets, and returns loaders with a fixed tuple layout.
5. [src/model_registry.py](src/model_registry.py) resolves `model_name` to `src.models.<name>.adapter`.
6. The adapter builds the model and translates the shared batch dictionary into that model’s expected forward signature.
7. Metrics, reports, and visualizations are generated by [src/metrics.py](src/metrics.py) and [src/analysis.py](src/analysis.py).

## Data contract that model authors must preserve

The most important implicit contract spans `src/data.py`, `src/trainer.py`, `src/evaluator.py`, `src/analysis.py`, and every model adapter.

Dataset batches come out of `HXDataset` as:
- training/testing: `(hsi_pca, hsi, aux, label)`
- visualization/inference grids: `(hsi_pca, hsi, aux, h, w)`

The framework then standardizes this into a batch dict with keys:
- `batch["hsi_pca"]`
- `batch["hsi"]`
- `batch["aux"]`
- `batch["label"]` when labels exist

New models should adapt to this contract in `adapter.py` rather than changing trainer/evaluator code.

Two practical consequences:
- HSI is available both as full-spectrum cube (`hsi`) and PCA-reduced tensor (`hsi_pca`); older models often use PCA only, newer ones may use full HSI.
- The trainer/evaluator/visualizer all assume adapter-based forwarding, so changing tuple order or batch key semantics will break multiple subsystems.

## Model integration pattern

Every model lives under `src/models/<model_name>/` and is exposed through three adapter functions:
- `build_model(config, dataset_type, device)`
- `forward_train(bundle, batch)`
- `forward_eval(bundle, batch)`

`MODEL_REGISTRY` in [src/model_registry.py](src/model_registry.py) is the only central registry. To add a model, register the adapter module there and keep the adapter thin; dataset-specific channel counts and class counts should come from `config.get_value(...)`, not be hardcoded in the trainer.

Look at these two patterns before modifying model integration:
- [src/models/fusatnet/adapter.py](src/models/fusatnet/adapter.py): PCA-based HSI input
- [src/models/rscnet/adapter.py](src/models/rscnet/adapter.py): mixed full-HSI + PCA + aux input

## Configuration system

[src/config.py](src/config.py) is the single source of truth for experiment parameters and output paths.

Important behavior:
- Dataset metadata (`out_features`, `data_channels`, `lidar_or_sar_channels`) is derived from `dataset_type` inside `ExperimentConfig`; do not duplicate this in models or scripts.
- Output paths under `model/`, `log/`, `report/`, and `pic/` are auto-generated from model name, dataset, and training parameters.
- The code still exposes `get_value()` / `set_value()` for compatibility, but those values are backed by the config manager.

When changing how experiments are launched, preserve the `ExperimentRunner -> config module global init -> trainer/evaluator` sequence in [src/runner.py](src/runner.py); several modules depend on that global config state being initialized.

## Data layout assumptions

The canonical data root is computed in [src/data.py](src/data.py) as the workspace-level `data/` directory adjacent to this repo, not `HSI-X-classify-backbone/data/` inside the repository. `scripts/train_all.py` uses the same convention through `src.data.DATA_ROOT`.

Before debugging missing-data failures, verify files exist under the external workspace data tree expected by `src.data.dataset_path(...)`.

Dataset-specific filename/key conventions are encoded directly in `src/data.py` and `scripts/train_all.py`; if you rename data files, update both places.

## Evaluation/reporting behavior

Testing is not just metric computation:
- [src/evaluator.py](src/evaluator.py) loads the entire saved model object with `torch.load(model_savepath[datasetType])`, so model class import paths must remain stable for old checkpoints to load.
- Reports are appended to text files in `report/` by [src/metrics.py](src/metrics.py).
- Visualization writes full-scene classification maps with dataset-specific shapes/color maps in [src/analysis.py](src/analysis.py).

If you change model outputs, keep them compatible with `np.argmax(logits, axis=1)` expectations across trainer, evaluator, metrics, and analysis.

## Repository-specific gotchas

- There is no established lint or unit test suite in this repository; validation is done through smoke training/testing scripts and real experiment runs.
- `scripts/strain.py` and `scripts/stest.py` are the fastest built-in verification entrypoints after model changes.
- `scripts/train_all.py` is useful for coverage across datasets/models because it skips missing datasets instead of crashing.
- The checked-in default training config at [configs/train.json](configs/train.json) currently targets `FGMambaHX`; if you want a different default experiment, update that file.
